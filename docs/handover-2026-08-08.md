- Windows 上 PyPI 默认 torch wheel 是 **+cpu** 版（约 122MB）——此前统一源时误以为
  "开发机无 NVIDIA GPU"而移除了 cu128 源，本次修正。
- cu128 索引 torch 最新为 2.11.0（PyPI 是 2.13.0），驱动需 ≥570。

## 2. 生产代码改动（本会话，未提交 → 随交接提交）

### 2.1 OCR 布局管线（4 文件 + 测试）— 核心成果
| 文件 | 改动 |
|---|---|
| `src/mbforge/backends/ocr/base.py` | `OCRResult` 加 `spans: list[LayoutSpan]`；新增 `LayoutSpan`（text/bbox/block_type），bbox 为 **PDF 点、bottom-left 原点**（与 PyMuPDF 一致） |
| `src/mbforge/backends/ocr/mineru.py` | `_extract_text_from_entry` 解析 ZIP 内 `layout.json` → `pdf_info[0].preproc_blocks` → spans；**y 轴翻转**（MinerU 是 top-left，转 bottom-left）；新静态方法 `_parse_layout_spans` |
| `src/mbforge/pipeline/extract_text.py` | `_ocr_pages` 把 OCR 结果的 spans 填入 `PageContent.text_spans`（此前 OCR 页永远为空 → ESMILES 永远页尾 fallback） |
| `src/mbforge/pipeline/esmiles_insert.py` | `_find_position_in_pages` 增强：分子框与 **image span**（图块）重叠时锚定到该图**后最近的文本 span**（原逻辑只查文本重叠，OCR 页必落空） |

**关键坐标事实**（经人工确认 h1 渲染假设）：
- MinerU layout.json bbox：**PDF 点、top-left 原点**（page_size=[595,842]），渲染时 ×(DPI/72) 不翻转；
- 分子检测 `bbox_pdf`：**PDF 点、bottom-left 原点**，渲染时 ×(DPI/72) 并翻转 y；
- spans 存进 `TextSpan.bbox` 用 **bottom-left**（与 `_find_position_in_pages`/`_bbox_overlap` 一致）。

**端到端实测**（WO2026037254A1，49 页全图扫描件）：452 个 ESMILES 块中 **390 锚定**到
结构式图注后文本行、62 页尾 fallback、0 错页、0 缺 `%% page=` 头。

## 4. 实验结论（本会话，真实 API 扣费）

### 4.1 文档 Markdown 对下游活性提取的结论
- OCR Markdown 与后续活性提取结果**逐行一致**（27/27 条 IC50，
  row_label+value_text 全同），提取侧都是确定性解析（0 次 LLM 调用）。
- **原因**：`_extract_tables_from_markdown` 自带 HTML `<table>`→Markdown 转换；
  `_parse_simple_activity_table` 确定性解析窄表（27 条 IC50 表一步拿下）。
- **结论**：当前摄取链路直接使用文档 Markdown，活性抽取不依赖额外文本变换。

### 4.2 Markush 被 normalize 拒绝（未解决，待决策）
- MolParser 对 Markush 通式输出 E-SMILES 含 `*`（连接点）和 `[Rb]`（R_b 基团，写成元素"铷"）。
- `DEFAULT_ALLOWED_ELEMENTS` 白名单把 `[Rb]` 当"R 基团误读"拒绝 → **专利核心结构进不了分子库**。
- Markdown 结构块会直接保留 MolParser 的 E-SMILES（包括 Markush 标签）；只有 normalize 挡路。
- 选项：白名单放行 `[Rb]`/`[Rc]` 等 MolParser Markush 约定 / 或单独 Markush 通道。**待决策**。
